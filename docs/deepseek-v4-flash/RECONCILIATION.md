# DeepSeek-V4-Flash-0731 — Reconciliation against `gitm.planner.moe_graph` (Part 1.3)

**Baseline operating point, restated:** one 8xH200 SXM node over NVLink, TP8, FP8
weights and KV where the checkpoint supports it, 32 active sequences in decode,
8,192 cached tokens each, one new token per sequence per step, text-only,
speculation disabled.

**What was audited.** The `sparse_moe` family (`gitm/planner/moe_graph.py`,
`SparseMoEModelSpec` in `gitm/planner/roofline.py`, `registry.detect_family`)
against the pinned checkpoint `deepseek-ai/DeepSeek-V4-Flash-0731 @ 7872f01b`:
its HF `config.json` (copied verbatim next to this file; sha256
`6c8f3d2d…0ae9a023`, matching the pinned original), its `inference/config.json`,
its `inference/model.py` (cited below as `model.py:N`), and the dtype and shape of
every tensor from the 48 shard headers (`shapes_summary.json`, regenerated by
`shapes_from_shards.py`). No serving engine is cited: the executable semantics are
the reference implementation's, and anything it leaves to an engine is labelled so.

**Naming boundary.** `model.py` reads the *inference* config's names
(`dim`, `n_layers`, `window_size`, `n_activated_experts`, `rope_head_dim`,
`moe_inter_dim`, `n_mtp_layers`); the planner reads the *HF* names
(`hidden_size`, `num_hidden_layers`, `sliding_window`, `num_experts_per_tok`,
`qk_rope_head_dim`, `moe_intermediate_size`, `num_nextn_predict_layers`). Every
citation of a `model.py` line in support of an HF key crosses that boundary; the
two files agree on every shared value except the MTP count (B7).

**Reproduce.** From the repo root with the project virtualenv:

```
python docs/deepseek-v4-flash/reconcile.py     # §1 key diff + planner floors per region (this branch)
python docs/deepseek-v4-flash/ledger.py        # checkpoint-side bytes and floors per region
gitm plan deepseek-v4-flash-0731 --gpu H200 --batch 32 --kv-len 8192 --tp 8   # at any commit
pytest tests/test_moe_graph.py                 # the four corrections each carry a test
```

## 0. Summary

Four discrepancies are corrected on this branch, one commit and one test each.
Nine further bugs and nine engine-dependent assumptions are documented below in
the blocker format (evidence, code path, consequence, fix, test), and ten places
where the class models the checkpoint exactly are recorded with the same
specificity, because "the dominant term is right" is as much a finding as "the
output projection is 8x wrong".

| Corrected | What the class did | Effect at the baseline, per rank per step |
|---|---|---|
| **B1** MTP head emitted with speculation off | priced 3 phantom full layers (46 of 43) | −0.173 ms (−6.1 %) |
| **B3** grouped output projection | `wo_a` 8x small: rank split *across* groups | +0.033 ms (+1.2 %); `attn_out_proj` 229 → 389 MB |
| **B5/B6** RoPE slice inside `head_dim` | q width and KV entry 576, checkpoint says 512 | −0.020 ms (−0.75 %); KV entry 640 → 576 B |
| **B9** shared expert dtype | priced at fp4 with the routed bank; it is fp8 | +0.013 ms (+0.5 %); `moe_shared` 96 → 159 MB |
| **net** | `gitm plan` 2.837 → **2.691 ms**, 636 → 600 nodes | −0.147 ms (−5.2 %) |

The corrections partially cancel in the total (−6.1 % against +2.5 %), which is
the reason a per-op comparison was required: a total-only check against a capture
would have passed within its own noise while every attention-side op was off.

**Headline.** The dominant term, routed-expert traffic (77 % of the planner's step,
67 % of the ledger's), is modelled **exactly**: fp4 payload, one e8m0 scale per
32 elements, the same distinct-expert union (§4.4, E1). The errors sit in what
runs at all (B1), in the attention-side weight accounting (B3, B4, B5/B6), in
per-tensor dtypes the family cannot express (B9 fixed; B11 not), and in a
footprint that counts one draft block where the checkpoint ships three (B7).
After the four fixes the planner's floor (2.691 ms) still sits 0.35 ms under the
ledger's (3.042 ms); §5 names where the rest is.

## 3. The module docstring's six claims, tested against the pinned checkpoint

1. *"Expert weight traffic is a set-union problem … `distinct_experts`, uniform
   routing."* The union is the right object and the formula is identical to the
   ledger's (E1, `ledger.py` asserts it). Uniformity is an assumption the checkpoint
   contradicts in kind on layers 0-2 (routing by token id, `:582`, so the expert
   histogram is the token histogram) and cannot confirm on 3-42 (`noaux_tc` with a
   learned bias, `:578-584`). Direction stated in the docstring (skew → fewer
   distinct → less traffic) is right. **U8.**
2. *"Attention is three mechanisms … CSA (compress + lightning indexer, `index_topk`)
   / HCA (heavier compression, dense, no indexer) / sliding window."* Confirmed for
   all 43 executed layers: `compress_ratios[layer_id]` (`:459`), ratio 4 → compressor
   and indexer (`:474`), other nonzero → compressor only (`:477`), 0 → neither; the
   read sizes 640 / 192 / 128 and the S/4 indexer scan match (`:433`, `:426`, `:513-520`).
   **E2-E4.** What the docstring does *not* say: the compressor is a pair of bf16
   linears run on every token (**B4**), the MTP tail of `compress_ratios` is
   sliding-window not CSA (**B2**), and HCA layers carry no index-key cache (**B13**).
3. *"Precision is per-tensor-class: experts fp4, linears fp8, KV fp8."* Routed
   experts fp4: **exact**, including the scale granularity (E1). "Experts" plural
   was wrong: the shared expert is fp8 (**B9**, fixed). "Linears fp8" holds for
   `wq_a`, `wq_b`, `wkv`, `wo_a`, `wo_b`, `indexer.wq_b`, shared expert; it does
   not hold for the router (bf16, run in fp32), mHC generators (fp32), `lm_head`
   and `embed` (bf16), compressors (bf16, run in fp32), `weights_proj` (bf16)
   (**B11**). "KV fp8": the checkpoint is QAT'd for it (`:532`) and the baseline
   requests it; the reference itself stores bf16 (**U1**).
4. *"Sharding per rank: TP splits heads and dense linears … TP does not divide KV
   traffic on a single-KV-head model."* The KV claim is **exact** (E5). "Dense
   linears split" is right for `wq_b`, `wo_a`, `wo_b`, `indexer.wq_b`; `wq_a`,
   `wkv`, the compressors, the router, the mHC generators and the shared expert
   are replicated in the reference (E9 for the first two; the rest are the
   engine-dependent replication terms in the design note §7). The indexer's
   `wq_b` is sharded and its score all-reduced (**U2**), the opposite of the
   planner's "ReplicatedLinear" reading.
5. *"Collectives are bandwidth-only, flagged `estimated`."* True as stated. The
   reference has two all-reduces per layer, both fp32 (`:182-183`, `:647`), plus
   the embedding (`:110`), the indexer score (`:429`, 21 layers) and the logits
   all-gather (`:738`): 109 per step against the planner's 43 (**U5, U6**).
6. *"Nodes marked `estimated`: grouped output projection, DSpark, every
   collective."* The output projection's flag was covering a shape that the
   checkpoint publishes (**B3**; the flag is removed with the fix). The DSpark
   flag covers a node that does not exist in the main stack (**B8**).

## 4. Findings

Classification: **bug** — the code derives a shape, dtype or schedule the
checkpoint contradicts; **unsupported assumption** — the code assumes what the
checkpoint neither confirms nor denies (engine-dependent or undocumented);
**exact** — the class matches the checkpoint. Magnitudes are per rank per step at
the baseline with the planner's H200 constants (HBM 4.8 TB/s), measured by
running `gitm plan` before and after each change; checkpoint-side bytes are
`ledger.py`'s.

### 4.1 Bugs corrected on this branch

**B1 — the MTP head is emitted with speculation disabled.**
*Evidence:* `Transformer.forward` (`model.py:913-926`) runs `self.layers` only;
the `mtp.*` blocks run in `forward_spec` (`:929-931`), a separate entry point a
non-speculative server never calls. The baseline disables speculation.
*Code path:* `predict_moe_graph`, `for i in range(spec.num_nextn_predict_layers)`
ran unconditionally, ignoring `BatchConfig.speculative_tokens`; `glm_graph` and
`hybrid_graph` already gate their draft heads on it.
*Consequence:* three phantom full layers (with the YAML's correct count of 3;
one with the HF config's 1): every `xN` 46 instead of 43, `moe_routed` +0.143 ms,
step **+0.173 ms (+6.1 %)**.
*Fix:* `if batch.speculative_tokens > 0:` around the loop. Footprint unchanged
(`model_weight_bytes` still counts the blocks: resident is not the same as run).
*Test:* `test_mtp_head_is_absent_without_speculation` (max layer is 42 at the
default batch; the footprint still exceeds the no-MTP footprint);
`test_mtp_head_emits_layers_beyond_the_stack` now passes `speculative_tokens=1`.

**B3 — the grouped output projection is 8x too small.**
*Evidence:* `wo_a = ColumnParallelLinear(n_heads·head_dim // n_groups, n_groups ·
o_lora_rank)` (`:468`), `wo_b = RowParallelLinear(n_groups · o_lora_rank, dim)`
(`:469`), applied as `einsum("bsgd,grd->bsgr", o, wo_a.view(groups, rank, -1))`
(`:542-546`): every group carries the **full** `o_lora_rank`, block-diagonally.
Shards: `wo_a.weight` F8 [8192, 4096], `wo_b.weight` F8 [4096, 8192] on every
layer; `:544` "wo_a is FP8 in checkpoint". Groups shard with the heads
(`n_local_groups = n_groups // world_size`, `:457`).
*Code path:* `_emit_layer` priced `wo_a` as `(n_heads·head_dim/tp) → o_lora_rank /
o_groups` (4096 → 128 per rank: 0.5 M elements against 4.2 M) and `wo_b` as
`o_lora_rank → h` with no `/tp` (right at TP8 only because 1024 = 8192/8; 8x
small at TP1); `model_weight_bytes` the same two terms. The node carried
`estimated=True` with the comment "the documented reading of the config and not
a published shape"; the shape is published.
*Consequence:* `attn_out_proj` 229 → 389 MB per rank per step, **+0.033 ms
(+1.2 %)**; resident +160 MB per rank. (The earlier scratch estimate of +316 MB
double-counted `wo_b`, which was already right at TP8.)
*Fix:* `group_width = n_heads·head_dim / o_groups`, `o_rank = o_groups·o_lora_rank
/ tp`; `wo_a = (group_width → o_rank)`, `wo_b = (o_rank → h)`; the `estimated`
flag removed; footprint terms `n_heads·head_dim·o_lora_rank / tp +
o_groups·o_lora_rank·h / tp`.
*Test:* `test_grouped_output_projection_carries_the_full_rank_per_group` pins
8192 × 4096 elements for each matrix and the per-rank bytes and FLOPs at TP1 and
TP8; `test_estimated_nodes_are_flagged` now expects `{"dspark"}` only.

**B5/B6 — the RoPE slice lives inside `head_dim`, so q width and KV entry are
512, not 576.**
*Evidence:* `nope_head_dim = head_dim − rope_head_dim` (`:455`); `wq_b` projects
to `n_heads · head_dim` (`:465`); `wkv = Linear(dim, head_dim)` (`:466`); the
cache buffer is `[B, kv_cache_size, head_dim]` (`:480`); RoPE rotates
`q[..., -rd:]` and `kv[..., -rd:]` (`:505`, `:510`); the fp8 simulation covers
`kv[..., :-rd]` with the comment "rope dims stay bf16" (`:511-512`). Shards:
`wq_b.weight` [32768, 1024] = 64 × 512; `wkv.weight` [512, 4096].
*Code path:* `SparseMoEModelSpec.q_head_dim` and `kv_latent_dim` returned
`head_dim + qk_rope_head_dim` (the DeepSeek-V3 `qk_nope_head_dim +
qk_rope_head_dim` convention applied to V4's keys), used by `attn_q_b`,
`attn_kv_a`, `attn_score_value`, `attn_qnorm_rope_insert`, `kv_entry_bytes`,
`model_weight_bytes`. The planner's own guard (`qk_rope_head_dim > head_dim`
raises: "the RoPE slice cannot be larger than the head it is a slice of") and
`kv_entry_bytes` (`rest = kv_latent_dim − rope`) already treated RoPE as a
*slice*, so the class was inconsistent with itself.
*Consequence:* KV entry 640.1 → 576.0 B (**−10 %** on every KV read and on the
KV ledger line, hence on the concurrency ceiling); `attn_score_value` 359 → 323
MB, `attn_kv_a` 314 → 281 MB, `attn_q_b` 218 → 195 MB; step **−0.020 ms
(−0.75 %)**.
*Fix:* `q_head_dim = head_dim`; `kv_latent_dim = num_kv_heads · head_dim`.
*Test:* `test_rope_slice_lives_inside_head_dim` (wq_b rows 32768, entry 512,
`kv_entry_bytes == 448 × fp8 + 64 × 2`); `test_kv_latent_is_shared_across_query_heads`
now pins 512.
*Not fixed here:* the reference's fp8 simulation scales the 448 dims per 64
(`:512`), 7 scale bytes per entry (583 B in the ledger). Whether a served cache
stores scales at that granularity is the engine's layout (U1); the planner's
per-entry constant stays at 576 B.

**B9 — the shared expert is fp8, not `expert_dtype`.**
*Evidence:* routed experts are built with `dtype=expert_dtype` (`:628-629`); the
shared expert with `Expert(args.dim, args.moe_inter_dim, swiglu_limit=…)`
(`:632`), i.e. on `default_dtype` = fp8 (`:884`, `:596-598`). Shards:
`ffn.shared_experts.{w1,w2,w3}.weight` F8_E4M3 with [16, 32] / [32, 16] scales
(128 × 128) on every layer.
*Code path:* `_emit_layer` priced `moe_shared` at `ew`/`ed`; `model_weight_bytes`
at `ew`.
*Consequence:* `moe_shared` 96 → 159 MB, **+0.013 ms (+0.5 %)**; resident +64 MB
per rank at the planner's `/tp`.
*Fix:* price at `ww`/`wd`; docstrings say routed experts only.
*Test:* `test_shared_expert_is_priced_at_weight_dtype` (bytes = 3·h·inter × fp8
within 1 % at one position; node dtype fp8).
*Still engine-dependent:* the planner divides the shared expert by `tp`; the
reference replicates it (plain `Linear`, `:632`, `:596-598`). 0.033 ms sharded
vs 0.236 ms replicated (`ledger.py` §H). Left as is, with both readings in the
design note §4.3.

### 4.2 Bugs left unpatched — blockers

Each in the form a blocking review comment would take.

**B2 — the MTP tail of `compress_ratios` is sliding-window; the class would price
it as CSA with an indexer.**
*Config evidence:* `config.json` `compress_ratios[43:46] = [0, 0, 0]`;
`DSparkBlock` gets `layer_id = n_layers + stage_id` (`:825`, `:902`), so
`compress_ratios[layer_id]` (`:459`) selects ratio 0; `DSparkAttention.forward`
asserts `compress_ratio == 0` (`:753`).
*Affected code path:* `spec_from_hf_config` drops the tail (`[:n_layers]`, with
the docstring calling it "MTP and padding slots"); `compress_ratio(layer)`
reuses the **last** entry for `layer ≥ len` (`roofline.py`), so MTP layers get
ratio 4 and an indexer.
*Expected consequence:* only under speculation (B1 gates it now): each MTP layer
carries an `attn_index_proj`, `attn_index_score` and a 640-entry core read where
the checkpoint runs a 128-token window; ≈ +0.004 ms per draft layer at B=32.
Also the third witness that the count is 3 (B7): 46 − 43.
*Proposed fix:* keep the tail as `mtp_compress_ratios` on the spec (or index MTP
layers into the untruncated list); `attention_kind(43..45) == "swa"`.
*Test:* `attention_kind(spec.n_layers) == "swa"` and no `attn_index_*` node with
`layer >= n_layers` under `speculative_tokens=1`. The existing
`test_compress_ratios_are_truncated` asserts the current behaviour and would be
rewritten to assert that the tail is *kept apart*, not dropped.
*Why not patched:* changes a documented, tested invariant of the class for a
path the baseline does not exercise.

**B4 — the KV compressors are bf16 linears run on every token, two per
compressor, with a second compressor inside each CSA indexer; the class prices
them as extra fp8 copies of `wkv`.**
*Config evidence:* per compressed layer `attn.compressor.wkv.weight` and
`wgate.weight` BF16, [1024, 4096] on CSA (`coff = 1 + overlap`, `:296-298`,
`:303-304`) and [512, 4096] on HCA, plus `ape` F32; CSA layers additionally hold
`attn.indexer.compressor.{wkv,wgate}` BF16 [256, 4096] (`:404`). All are plain
`Linear` (replicated). The projections run on every token in fp32 (`:327-330`);
only the pooling has the 1/r duty cycle (`:350`).
*Affected code path:* `_emit_layer`, `n_kv_proj = {"csa": 4, "hca": 2}` widening
`attn_kv_a`: 4 or 2 copies of a 512-wide fp8 projection, sharded by nothing but
also not by tp; `attn_kv_compress` prices the pooling only.
*Expected consequence:* per rank per step the checkpoint reads `wkv` (2.1 MB ×
43) plus compressors (CSA 21.0 MB × 21, HCA 8.4 MB × 20) ≈ 704 MB against the
planner's `attn_kv_a` 281 MB: **≈ +0.09 ms (+3.3 %)**, and TP cannot reduce it.
Resident +0.61 GB per rank (`ledger.py` §A, `compressor` class). If an engine
keeps the reference's fp32 upcast in HBM, double that (`ledger.py` §H).
*Proposed fix:* a `attn_kv_compress_proj` node per compressor (main, and indexer on
CSA) with its own dtype (`compressor_dtype`, default bf16) and width `coff ·
head_dim`, replicated; drop `n_kv_proj`.
*Test:* on a CSA layer, `attn_kv_compress_proj` bytes = 2 × (1024 × 4096) × 2 +
2 × (256 × 4096) × 2 within 1 % at one position; on HCA 2 × (512 × 4096) × 2; none
on SWA.
*Why not patched:* needs a new node and a new spec field (a dtype the family
cannot express), and the node name must be chosen against
`docs/kernel_identity.md` so a capture can pair it; that is a family change, not
a two-line fix.

**B7 — `num_nextn_predict_layers: 1` is wrong; the checkpoint ships three MTP
blocks, each a full MoE layer.**
*Config evidence:* the safetensors index carries `mtp.0`, `mtp.1`, `mtp.2`
(4,705 tensors, 10.86 GB); `inference/config.json` says `n_mtp_layers: 3`;
`compress_ratios` has exactly 3 trailing entries; `model.py:900-902` builds
`n_mtp_layers` `DSparkBlock`s, each a full `Block` (`:818-823`). The HF key is
the outlier, and it is the one the class reads.
*Affected code path:* `spec_from_hf_config` (`num_nextn_predict_layers`);
`model_weight_bytes` adds that many layers; the docstring there says 0731's
extra 7 GB is DSpark "whose shape is not public" — it is public, it is `mtp.1`
and `mtp.2`.
*Expected consequence:* 0 ms at the baseline (B1). Footprint: one block
(≈ 3.6 GB / 8 = 0.45 GB per rank) counted where three ship (1.50 GB per rank,
`ledger.py` §D), *if* the engine loads them (U9). `test_dspark_variant_is_a_lower_bound_not_an_estimate`
asserts the under-count (`delta < published_delta / 100`) as a guard against
"fitting a number"; with the correct count the delta is ≈ 10.9 GB against a
published 7 GB, and the test fails by design.
*Proposed fix:* the YAML on this branch sets 3 with provenance (the catalogue
path is unaffected by the HF key). For the config path: read
`num_nextn_predict_layers` but warn when `compress_ratios` has a longer tail;
rewrite the docstring and replace the guard test with one that pins the footprint
delta to `3 × one layer's bytes` within 5 %.
*Why not patched:* the HF value is the checkpoint's own claim; overriding a config
key inside the reader from a second file is a policy change (which file wins)
that deserves its own review.

**B8 — the `dspark` node on layers 40-42 is a phantom.**
*Config evidence:* `dspark_target_layer_ids` names the layers whose hidden state
is **collected** (`:918-921`: `main_hiddens.append(h.mean(dim=2))`, nothing
else); the projection that consumes them, `main_proj` [4096, 12288], lives in
`mtp.0` (`:832`) and runs in `forward_spec` only. No `layers.4x.dspark*` tensor
exists in the index.
*Affected code path:* `_emit_layer`, `if layer in spec.dspark_layer_ids:` emits an
`estimated` low-rank down-up pair; `model_weight_bytes` adds `2·h·rank` per
target layer.
*Expected consequence:* 0.0005 ms per step and 2.4 MB: a wrong node, not a wrong
total. It matters for pairing: a predicted node with no kernel behind it is a
permanent unmatched residual.
*Proposed fix:* delete the node and the footprint term; keep `dspark_layer_ids`
on the spec for the `mean` collection (a pointwise op, priced at zero bytes of
weights) if a node is wanted for pairing.
*Test:* no node with `op == "dspark"` for the 0731 spec; `main_proj` counted in
the MTP footprint. Retarget `test_dspark_only_on_its_declared_layers`.
*Why not patched:* the kernel-identity test maps `dspark_markov_update_kernel`
to `dspark`, so *some* engine emits a kernel by that name. Without a pinned engine
I cannot say what it computes or on which layers; what the checkpoint
establishes is only that no such weights exist in the main stack.

**B10 — hash-routed layers still run the router GEMM.**
*Config evidence:* `scores = linear(x.float(), self.weight.float())` (`:570`)
runs on every layer; hashing replaces `indices` only (`:582`), and `weights` are
gathered from `scores` (`:585`). `layers.{0,1,2}.ffn.gate.weight` BF16 [256, 4096]
exists alongside `tid2eid` I64 [129280, 6].
*Affected code path:* `_emit_layer`, `if layer >= spec.num_hash_layers:` skips
`moe_router`; `roofline.py` field comment "those layers run no router GEMM".
*Expected consequence:* 3 missing nodes, ≈ 6 MB and 0.001 ms; plus a 6 × 8 B
gather per token from a 6 MB table. Wrong in kind (an observed kernel with no
predicted node), negligible in ms.
*Proposed fix:* emit `moe_router` on every layer; on hash layers add the
`tid2eid` gather bytes.
*Test:* `moe_router` count == `n_layers` for the 0731 spec.
*Why not patched:* one line, but it reverses a documented design claim of the
family (`roofline.py`) and I did not want to bundle it with the four
measured corrections; it is the first thing to take after B4.

**B11 — router, mHC generators, `lm_head`/`embed`, compressors and
`weights_proj` are not `weight_dtype`.**
*Config evidence:* `ffn.gate.weight` BF16 (computed in fp32, `:570`);
`hc_attn_fn`/`hc_ffn_fn` F32 [24, 16384] (`:670-674`); `head.weight` and
`embed.weight` BF16 ("lm_head in the checkpoint is stored in bf16", `:728`);
compressors BF16 (`:303-304`); `indexer.weights_proj` BF16 (`:400`); `attn_sink`
F32.
*Affected code path:* every `add(..., wd)` for those ops in `_emit_layer` and
`predict_moe_graph` (`lm_head`), and `model_weight_bytes` (`embed`, router, mHC
at `ww`). The family has no `op_dtype_overrides`; the `glm_moe_dsa` family grew
one for exactly this (`docs/glm-5.2/DESIGN-NOTE.md` §7.1 G1).
*Expected consequence:* mHC +101 MB per rank per step (fp32 vs fp8, replicated),
which the planner's launch floor currently masks (`mhc_mix` is launch-bound at
86 × 2 µs = 0.172 ms; its memory term rises by 0.021 ms and stays under);
`lm_head` 66 → 132 MB, +0.014 ms; router +43 MB, +0.009 ms. **≈ +0.02-0.05 ms
(+1-2 %)** depending on the launch constant; resident +0.24 GB per rank.
*Proposed fix:* port `op_dtype_overrides` from `glm_graph` (`add()` and
`model_weight_bytes` consult it before the family default); populate it from the
shard headers in the YAML (`moe_router: bf16`, `mhc_mix: fp32`, `lm_head: bf16`).
*Test:* the same shape as GLM's: a spec with overrides prices `lm_head` bytes at
2 × vocab/tp × h within 1 % at one position.
*Why not patched:* a cross-cutting spec change whose GLM precedent took a design
note section; the magnitudes are small enough at the baseline to document first.

**B12 — every layer holds a 128-token window buffer, not only the two SWA
layers.**
*Config evidence:* `kv_cache_size = window_size + (max_seq_len // ratio if ratio
else 0)` for every layer (`:479`); on compressed layers the window indices are
concatenated with the compressed ones (`:513`, `:520`).
*Affected code path:* `kv_fixed_bytes_per_sequence` counts `swa_layers` only.
`effective_kv_tokens` **does** include the window on CSA/HCA, so the per-step
read is right and only the footprint is wrong.
*Expected consequence:* 41 layers × 128 × 576 B ≈ 3.0 MB per sequence, 97 MB per
rank at B=32 (replicated). Ledger-only; 0 ms.
*Proposed fix:* count all `n_layers` in `kv_fixed_bytes_per_sequence`.
*Test:* `kv_fixed_bytes_per_sequence(spec) == n_layers × sliding_window ×
kv_entry_bytes(spec)`; `test_kv_footprint_splits_growing_from_fixed` pins the
current 2-layer value and would change with it.
*Why not patched:* the existing test encodes the opposite reading with a
rationale ("worth ~40 tokens of context"); changing it needs the reviewer to
agree the reference's buffer layout, not a paged engine's, is what the footprint
should follow.

**B13 — HCA layers are charged an index-key cache they do not have.**
*Config evidence:* HCA builds no `Indexer` (`:477`), hence no `indexer.kv_cache`
(`:405`).
*Affected code path:* `kv_bytes_per_token` adds `index_head_dim × kw / r` for every
compressed layer.
*Expected consequence:* 20 layers × 128 B / 128 = 20 B per token of context, 0.4 %
of the KV rate. Negligible; wrong in kind.
*Proposed fix:* add the index-key term only when `attention_kind(layer) == "csa"`.
*Test:* `kv_bytes_per_token(spec) == Σ_csa (entry + 128·kw)/4 + Σ_hca entry/128`.
*Why not patched:* one line, bundled with B12 in the same function; both are
footprint-only and below the ledger's own allowance lines.

## 5. Ranking by expected modelling error at the baseline

Per rank per step, planner H200 constants. Signs matter: the two largest are
opposite, so the total hides them.

1. **B1** phantom MTP layers: −0.173 ms (−6.1 %). Fixed.
2. **B4** compressor dtype, shape and count: ≈ +0.09 ms (+3.3 %) and +0.61 GB
   resident; TP cannot reduce it. Blocker.
3. **B3** grouped output projection: +0.033 ms (+1.2 %), +0.16 GB resident. Fixed.
4. **B11** per-op dtypes (mHC fp32, `lm_head`/`embed`/router bf16): +0.02-0.05
   ms (+1-2 %), +0.24 GB resident. Blocker.
5. **B5/B6** 576 vs 512: −0.020 ms (−0.75 %) and −10 % on the KV footprint. Fixed.
6. **B9** shared expert fp8: +0.013 ms (+0.5 %). Fixed.
7. **B7 + U9** MTP count 1 vs 3 and residency: 0 ms; ±1.0-1.5 GB per rank on the
   footprint. Blocker (YAML carries 3).
8. **U1-U9**: not errors; each with its resolving observation. The largest in
   ms if the reference's reading holds: shared expert replicated (+0.20 ms),
   collectives 109 vs 43 (+0.07 ms at bandwidth, far more at a latency floor),
   bf16 KV store (+0.05 ms).
9. **B2, B8, B10, B12, B13**: wrong in kind, ≤ 0.001 ms each.

Where the remaining 0.35 ms between `gitm plan` (2.691 ms) and the ledger
(3.042 ms) sits: shared-expert replication 0.20 (U), compressors 0.09 (B4),
collectives 0.07 (U5/U6), dtypes 0.02-0.05 (B11), against −0.03 for the mHC
launch floor the ledger does not price. The dominant term differs by 0.003 ms.

## 6. Corrected versus left unpatched, and why

**Corrected (four commits, one test each):** B1, B3, B5/B6, B9. Each is proven
by a `model.py` line *and* a stored tensor shape or dtype, each fix is a few lines
in one function or property, each moved a measured number, and each keeps the
suite green (1,229 passed after the four changes, from 1,225; `ruff` clean;
pre-commit hooks pass). B1 also aligns the family with the repo's two other
families, which already gate their draft heads on `speculative_tokens`.

**Left unpatched, with a blocker each:** B4 and B11 need a new node or a new spec
field (a dtype the family cannot express), and node names that a capture can pair
against; B7 needs a policy on which config file wins; B2, B8, B10, B12, B13 are
one-liners that each reverse a documented, tested claim of the class for ≤ 0.001
ms at the baseline, and bundling them with the measured fixes would have made the
review harder than the gain. B8 in particular cannot be settled from the
checkpoint alone because a kernel by that name exists in the repo's own identity
table.

**Not touched on purpose:** `distinct_experts`, the attention-kind schedule, the
fp4 constant, the KV-not-divided-by-TP rule (E1-E5). They are right, and the case
names "changing planner code to demonstrate activity" as a failure mode.
